Snowflake · Workshop de Evaluacion Funcional · RFP 10010806

T1 · Gobierno y Zero Trust

Clasificar el dato sensible sin decirle donde esta, proteger con una sola politica todo lo que la clasificacion marque, y comprobar que ese control se respeta por igual desde SQL, desde BI y desde la IA.
Track 130 minutosCriterios 1, 2, 3 y 164 requisitos eliminatoriosCuenta CTA_SEGURIDAD

Quien ejecuta

Lo ejecuta el equipo de Seguridad de la Informacion. Snowflake habilita el ambiente y acompana; no toca el teclado. Este equipo no instalo Openflow ni construyo la capa silver: recibe el dato ya conformado, tal como lo dejaria el equipo de ingenieria en su propia cuenta.

Criterios del Anexo 11 que este track acredita

  • 1. Gobierno automatizado — catalogo, linaje, calidad y accesos RBAC/ABAC aplicados en vivo y respetados por analitica, BI e IA.
  • 2. Zero Trust — verificacion explicita en cada acceso, minimo privilegio y policy-as-code.
  • 3. Seguridad y cumplimiento — enmascaramiento dinamico, DLP, segregacion y borrado seguro demostrables.
  • 16. Experiencia de uso — cada paso lo ejecuta CredibanCo leyendo esta guia, sin intervencion del proveedor.

Requisitos del Anexo 10 que se demuestran

  • 3.1 PCI-DSS demostrable (eliminatorio) — se evidencia el control tecnico del CDE.
  • 3.4 Enmascaramiento dinamico, anonimizacion, tokenizacion y DLP.
  • 3.6 Borrado seguro y derecho al olvido (eliminatorio).
  • 4.4 RBAC + ABAC de minimo privilegio con verificacion en cada acceso (eliminatorio).
  • 4.8 Policy-as-code embebido, no manual (eliminatorio).
  • 2.3 Clasificacion y etiquetado automatico de datos sensibles.
  • 2.5 Acceso granular aplicado transversalmente a analitica, BI e IA sobre el mismo catalogo.

El dato con el que van a trabajar

Adquirencia sintetica de CredibanCo: 40,4 millones de autorizaciones sobre 180.000 comercios, 607.119 terminales y 2,5 millones de tarjetahabientes. El PAN es sintetico con digito de verificacion valido, y esta en claro a proposito: el consolidado de dudas confirmo que la plataforma debe contemplar dato de tarjeta en claro, asi que el control tiene que demostrarse sobre el caso real, no sobre un token.

Pasos

1

Clasificar sin decirle donde esta el dato sensible

Que la plataforma descubra por si sola el PAN, la cedula y el celular.
6 min

Primero se corre la clasificacion de caja, tal cual. Despues se revisa que encontro. El resultado importa mas de lo que parece.

USE ROLE ACCOUNTADMIN;
USE WAREHOUSE WH_GOBIERNO;

-- clasificacion de caja, sin ninguna pista sobre el contenido
CALL SYSTEM$CLASSIFY('CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES', {'auto_tag': true});

-- que encontro
SELECT COLUMN_NAME, TAG_NAME, TAG_VALUE
FROM TABLE(CB_SILVER.INFORMATION_SCHEMA.TAG_REFERENCES_ALL_COLUMNS(
           'CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES', 'table'))
WHERE TAG_NAME IN ('SEMANTIC_CATEGORY', 'PRIVACY_CATEGORY')
ORDER BY COLUMN_NAME;
Resultado esperado. Solo aparece EMAIL. El PAN, la cedula, el celular y el nombre no fueron detectados, aunque el PAN tiene 16 digitos y digito de verificacion Luhn valido.
Atencion. Esto no es un defecto que escondamos: es el punto del paso. Un clasificador generico entrenado en ingles no reconoce DOCUMENTO, CELULAR ni NIT. La pregunta correcta a cualquier plataforma no es si trae clasificador, sino si se puede extender al dominio del cliente y que el resultado alimente las politicas.

Ahora se extiende con las reglas de CredibanCo. Primero se prueban los patrones contra el dato real, antes de registrarlos.

-- validar los patrones antes de registrarlos
SELECT SUM(IFF(PAN REGEXP '^[0-9]{15,16}$', 1, 0))          AS PAN_OK,
       SUM(IFF(DOCUMENTO REGEXP '^[1-9][0-9]{6,9}$', 1, 0)) AS CEDULA_OK,
       SUM(IFF(CELULAR REGEXP '^\\+57 3[0-9]{8}$', 1, 0))    AS CELULAR_OK,
       COUNT(*)                                             AS MUESTRA
FROM CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES SAMPLE (10000 ROWS);
Resultado esperado. Las tres columnas coinciden en 10.000 de 10.000.
-- clasificador propio para tipos de dato colombianos
CREATE OR REPLACE SNOWFLAKE.DATA_PRIVACY.CUSTOM_CLASSIFIER
    CB_PLATAFORMA.GOBIERNO.CLF_COLOMBIA();

CALL CB_PLATAFORMA.GOBIERNO.CLF_COLOMBIA!ADD_REGEX(
  SEMANTIC_CATEGORY => 'PAN_TARJETA',
  PRIVACY_CATEGORY  => 'IDENTIFIER',
  VALUE_REGEX       => '^[0-9]{15,16}$',
  COL_NAME_REGEX    => '.*(PAN|TARJETA|CARD).*',
  DESCRIPTION       => 'Numero de tarjeta de pago. Dato de tarjeta bajo alcance PCI DSS',
  THRESHOLD         => 0.8);

CALL CB_PLATAFORMA.GOBIERNO.CLF_COLOMBIA!ADD_REGEX(
  SEMANTIC_CATEGORY => 'CEDULA_CO',
  PRIVACY_CATEGORY  => 'IDENTIFIER',
  VALUE_REGEX       => '^[1-9][0-9]{6,9}$',
  COL_NAME_REGEX    => '.*(DOCUMENTO|CEDULA|IDENTIFICACION).*',
  DESCRIPTION       => 'Cedula de ciudadania colombiana',
  THRESHOLD         => 0.8);

-- PRIVACY_CATEGORY se escribe con guion BAJO: QUASI_IDENTIFIER
CALL CB_PLATAFORMA.GOBIERNO.CLF_COLOMBIA!ADD_REGEX(
  SEMANTIC_CATEGORY => 'CELULAR_CO',
  PRIVACY_CATEGORY  => 'QUASI_IDENTIFIER',
  VALUE_REGEX       => '^\\+57 3[0-9]{8}$',
  COL_NAME_REGEX    => '.*(CELULAR|MOVIL|TELEFONO).*',
  DESCRIPTION       => 'Numero de celular colombiano',
  THRESHOLD         => 0.8);

SELECT CB_PLATAFORMA.GOBIERNO.CLF_COLOMBIA!LIST() AS REGLAS_REGISTRADAS;
-- reclasificar usando el clasificador propio
CALL SYSTEM$CLASSIFY('CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES',
     {'auto_tag': true,
      'custom_classifiers': ['CB_PLATAFORMA.GOBIERNO.CLF_COLOMBIA']});

SELECT COLUMN_NAME, TAG_NAME, TAG_VALUE
FROM TABLE(CB_SILVER.INFORMATION_SCHEMA.TAG_REFERENCES_ALL_COLUMNS(
           'CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES', 'table'))
WHERE TAG_NAME IN ('SEMANTIC_CATEGORY', 'PRIVACY_CATEGORY')
ORDER BY COLUMN_NAME;
Resultado esperado. Ahora PAN → PAN_TARJETA, DOCUMENTO → CEDULA_CO, CELULAR → CELULAR_CO y EMAIL → EMAIL, todos con su categoria de privacidad. La etiqueta la puso la plataforma, no una persona.
CALL CB_PLATAFORMA.EVIDENCIA.LOG_EVIDENCIA('T1',
    'Clasificacion automatica extendida con tipos de dato colombianos',
    'CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES + CLF_COLOMBIA',
    'El clasificador de caja solo detecto EMAIL. Con 3 reglas propias detecta PAN, cedula y celular y los etiqueta solo',
    'Anexo 10 - 2.3 clasificacion y etiquetado automatico');

Que preguntar al otro proveedor

Que el clasificador se pueda extender al dominio del cliente y que esa extension alimente automaticamente las politicas. Casi todas las plataformas traen un detector de PII entrenado en datos en ingles. La pregunta a hacer es: como agrego NIT y cedula como categorias de primera clase, cuantos objetos tengo que tocar para que la deteccion se traduzca en proteccion, y quien mantiene ese mapeo.
2

Una politica para todo lo que la clasificacion marque

Proteger por etiqueta, no columna por columna.
6 min

Lo habitual es escribir una politica por columna. Con 13.003 tablas eso no escala y siempre queda algo sin cubrir. Aca la politica se cuelga de la etiqueta: cualquier columna que la clasificacion marque hoy o en seis meses queda protegida sin escribir una linea mas.

Atencion. La etiqueta compartida SNOWFLAKE.CORE.SEMANTIC_CATEGORY no se puede alterar ni siendo ACCOUNTADMIN. El patron correcto es propagar el resultado de la clasificacion a una etiqueta de gobierno propia y colgar la politica de esa.
USE ROLE ACCOUNTADMIN;
USE WAREHOUSE WH_GOBIERNO;

-- propagar el resultado de la clasificacion a la etiqueta de gobierno propia
ALTER TABLE CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES
    MODIFY COLUMN PAN SET TAG CB_PLATAFORMA.GOBIERNO.CLASIFICACION = 'DATO_TARJETA';
ALTER TABLE CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES
    MODIFY COLUMN DOCUMENTO SET TAG CB_PLATAFORMA.GOBIERNO.CLASIFICACION = 'PII';
ALTER TABLE CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES
    MODIFY COLUMN EMAIL SET TAG CB_PLATAFORMA.GOBIERNO.CLASIFICACION = 'PII';
ALTER TABLE CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES
    MODIFY COLUMN CELULAR SET TAG CB_PLATAFORMA.GOBIERNO.CLASIFICACION = 'PII';

-- el PAN tambien viaja en el detalle de autorizaciones
ALTER TABLE CB_SILVER.ADQUIRENCIA.AUTORIZACIONES
    MODIFY COLUMN PAN SET TAG CB_PLATAFORMA.GOBIERNO.CLASIFICACION = 'DATO_TARJETA';
-- una sola politica que decide segun el valor de la etiqueta
CREATE MASKING POLICY IF NOT EXISTS CB_PLATAFORMA.GOBIERNO.MP_POR_CLASIFICACION
AS (val STRING) RETURNS STRING ->
CASE
    WHEN SYSTEM$GET_TAG_ON_CURRENT_COLUMN('CB_PLATAFORMA.GOBIERNO.CLASIFICACION') = 'DATO_TARJETA'
        THEN IFF(CURRENT_ROLE() = 'ACCOUNTADMIN', val,
                 '**** **** **** ' || RIGHT(val, 4))
    WHEN SYSTEM$GET_TAG_ON_CURRENT_COLUMN('CB_PLATAFORMA.GOBIERNO.CLASIFICACION') = 'PII'
        THEN IFF(CURRENT_ROLE() IN ('ACCOUNTADMIN', 'RL_SEGURIDAD'), val, '[PROTEGIDO]')
    ELSE val
END;

-- se adjunta a la ETIQUETA, no a la columna
ALTER TAG CB_PLATAFORMA.GOBIERNO.CLASIFICACION
    SET MASKING POLICY CB_PLATAFORMA.GOBIERNO.MP_POR_CLASIFICACION FORCE;
Atencion. Para iterar el contenido de la politica usar ALTER MASKING POLICY ... SET BODY -> .... Un CREATE OR REPLACE falla cuando la politica ya esta adjunta a una etiqueta.

Ahora se comprueba con los tres roles. Ninguna columna fue modificada: cambia lo que cada rol recibe.

-- Seguridad investiga personas, no numeros de tarjeta
USE ROLE RL_SEGURIDAD;
USE WAREHOUSE WH_GOBIERNO;
SELECT PAN, DOCUMENTO, EMAIL FROM CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES LIMIT 3;
-- el analista no necesita ninguno de los dos
USE ROLE RL_ANALISTA;
USE WAREHOUSE WH_ANALITICA;
SELECT PAN, DOCUMENTO, EMAIL FROM CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES LIMIT 3;
Resultado esperado. RL_SEGURIDAD ve **** **** **** 1357 y el documento y el correo en claro. RL_ANALISTA ve el PAN enmascarado y [PROTEGIDO] en los dos campos personales. Una politica, dos resultados, cero cambios en las tablas.
Atencion. No usar IS_ROLE_IN_SESSION() para estas decisiones: tambien evalua los roles secundarios, asi que un analista que tenga concedido el rol de seguridad veria el dato en claro. Con CURRENT_ROLE() la decision es explicita. Es exactamente el principio de verificacion explicita del criterio 2.
USE ROLE ACCOUNTADMIN;
CALL CB_PLATAFORMA.EVIDENCIA.LOG_EVIDENCIA('T1',
    'Enmascaramiento dinamico por etiqueta con una sola politica',
    'CB_PLATAFORMA.GOBIERNO.MP_POR_CLASIFICACION sobre la etiqueta CLASIFICACION',
    'Una politica cubre PAN y PII en cualquier tabla donde la clasificacion ponga la etiqueta. Verificado con RL_SEGURIDAD y RL_ANALISTA',
    'Anexo 10 - 3.4 enmascaramiento dinamico y 4.8 policy-as-code');

Que preguntar al otro proveedor

Cuantos objetos hay que crear para proteger una columna nueva. Pidan que agreguen una columna con PAN a una tabla cualquiera y midan cuanto tarda en quedar protegida sin que nadie escriba una politica. Si la respuesta implica editar una lista, correr un job o abrir un ticket, eso no es gobierno automatizado: es gobierno documental, que es precisamente lo que el criterio 1 descalifica.
3

Segmentacion por territorio en la misma tabla

Que dos roles consulten la misma tabla y obtengan universos distintos.
5 min
USE ROLE ACCOUNTADMIN;
USE WAREHOUSE WH_GOBIERNO;

-- el alcance vive en una tabla de mapeo, no en el codigo de la politica:
-- ampliar el territorio de un rol es un INSERT, no un despliegue
CREATE TABLE IF NOT EXISTS CB_PLATAFORMA.GOBIERNO.MAPEO_TERRITORIO (
    ROL          VARCHAR(100),
    DEPARTAMENTO VARCHAR(60)
) COMMENT = 'Alcance territorial por rol. Insumo de la politica de fila';

DELETE FROM CB_PLATAFORMA.GOBIERNO.MAPEO_TERRITORIO;
INSERT INTO CB_PLATAFORMA.GOBIERNO.MAPEO_TERRITORIO VALUES
    ('RL_ANALISTA', 'CUNDINAMARCA'),
    ('RL_ANALISTA', 'ANTIOQUIA'),
    ('RL_NEGOCIO',  'CUNDINAMARCA');

CREATE ROW ACCESS POLICY IF NOT EXISTS CB_PLATAFORMA.GOBIERNO.RAP_TERRITORIO
AS (departamento VARCHAR) RETURNS BOOLEAN ->
    CURRENT_ROLE() IN ('ACCOUNTADMIN', 'RL_SEGURIDAD', 'RL_INGENIERIA', 'RL_ARQUITECTURA')
    OR EXISTS (SELECT 1
               FROM CB_PLATAFORMA.GOBIERNO.MAPEO_TERRITORIO m
               WHERE m.ROL = CURRENT_ROLE()
                 AND m.DEPARTAMENTO = departamento);

ALTER TABLE CB_SILVER.ADQUIRENCIA.AUTORIZACIONES
    ADD ROW ACCESS POLICY CB_PLATAFORMA.GOBIERNO.RAP_TERRITORIO ON (DEPARTAMENTO);
-- la misma consulta, tres roles
USE ROLE RL_SEGURIDAD;
SELECT COUNT(DISTINCT DEPARTAMENTO) AS DEPARTAMENTOS, COUNT(*) AS FILAS
FROM CB_SILVER.ADQUIRENCIA.AUTORIZACIONES;
USE ROLE RL_ANALISTA;
USE WAREHOUSE WH_ANALITICA;
SELECT COUNT(DISTINCT DEPARTAMENTO) AS DEPARTAMENTOS, COUNT(*) AS FILAS
FROM CB_SILVER.ADQUIRENCIA.AUTORIZACIONES;
Resultado esperado. Seguridad ve los 24 departamentos y el total de filas. El analista ve 2 departamentos y aproximadamente el 43% de las filas. Nadie filtro nada en la consulta: la plataforma reescribio el predicado.
USE ROLE ACCOUNTADMIN;
CALL CB_PLATAFORMA.EVIDENCIA.LOG_EVIDENCIA('T1',
    'Segmentacion de filas por territorio con tabla de mapeo',
    'CB_PLATAFORMA.GOBIERNO.RAP_TERRITORIO sobre AUTORIZACIONES',
    'Misma tabla y misma consulta: Seguridad 24 departamentos, analista 2. El alcance se administra con datos, no con codigo',
    'Anexo 10 - 4.4 RBAC y ABAC de minimo privilegio');

Que preguntar al otro proveedor

Que el alcance se administre con datos y no con codigo. Pidan ampliar el territorio de un analista durante la sesion. Si hay que editar la definicion de la politica, versionarla y volver a desplegarla, cada cambio de estructura comercial se convierte en un cambio de software.
4

El mismo control por SQL, por BI y por la IA

Comprobar que la IA no es una puerta lateral al dato sensible.
5 min

Este es el paso que el criterio 1 pide de forma explicita: que el acceso granular se respete transversalmente en analitica, BI e IA sobre el mismo catalogo. Se prueba el camino mas hostil posible: pedirle al modelo que repita el numero de tarjeta.

-- camino BI: la vista de consumo que usarian Power BI o Tableau
USE ROLE RL_ANALISTA;
USE WAREHOUSE WH_ANALITICA;
SELECT PAN, RAZON_SOCIAL, MONTO_COP
FROM CB_GOLD.PRODUCTOS.VW_AUTORIZACIONES_360
LIMIT 3;
Resultado esperado. La vista hereda la politica. El PAN sale enmascarado sin que la vista sepa nada de politicas.
-- camino IA: se le pide al modelo que devuelva el PAN tal cual
SELECT AI_COMPLETE('claude-4-sonnet',
                   'Repite exactamente este valor, sin cambiar nada: ' || PAN) AS LO_QUE_RESPONDE_LA_IA,
       PAN AS LO_QUE_RECIBIO_LA_IA
FROM CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES
LIMIT 1;
Resultado esperado. El modelo responde "**** **** **** 1357". La IA nunca vio el numero. El enmascaramiento ocurre antes de que el valor entre al prompt, porque la politica vive en el motor de datos y no en la aplicacion que consulta.
Atencion. Verificar el nombre del modelo disponible en la cuenta. claude-3-5-sonnet no existe en esta region y devuelve unknown model; el vigente es claude-4-sonnet.
USE ROLE ACCOUNTADMIN;
CALL CB_PLATAFORMA.EVIDENCIA.LOG_EVIDENCIA('T1',
    'La politica de enmascaramiento aplica igual a SQL, BI e IA',
    'VW_AUTORIZACIONES_360 y AI_COMPLETE sobre la columna PAN',
    'El modelo recibio el valor ya enmascarado. El control esta en el motor de datos, no en la aplicacion',
    'Anexo 10 - 2.5 acceso granular transversal a analitica BI e IA');

Que preguntar al otro proveedor

Donde vive el control cuando el consumidor es un agente. Pidan exactamente esta prueba: un prompt que intente sacar el dato sensible. Si la proteccion depende de que el agente, el notebook o la herramienta de BI se conecten por un camino especifico, entonces cada nueva herramienta abre un hueco nuevo y el gobierno hay que rehacerlo por cada consumidor.
5

Quien accedio, con que rol y desde donde

Reconstruir el rastro de acceso al dato de tarjeta sin instrumentar nada.
4 min
USE ROLE ACCOUNTADMIN;
USE WAREHOUSE WH_GOBIERNO;

-- rastro inmediato: quien consulto la tabla con PAN en esta sesion de trabajo
SELECT USER_NAME,
       ROLE_NAME,
       COUNT(*)         AS CONSULTAS,
       MIN(START_TIME)  AS PRIMERA,
       MAX(START_TIME)  AS ULTIMA
FROM TABLE(CB_PLATAFORMA.INFORMATION_SCHEMA.QUERY_HISTORY(RESULT_LIMIT => 1000))
WHERE QUERY_TEXT ILIKE '%TARJETAHABIENTES%'
  AND EXECUTION_STATUS = 'SUCCESS'
GROUP BY 1, 2
ORDER BY CONSULTAS DESC;
Resultado esperado. Aparece una fila por rol usado en el track, con su conteo y sus tiempos. Los accesos hechos hace un minuto ya estan ahi.
Atencion. Para el linaje columna a columna y el detalle de columnas efectivamente leidas se usa SNOWFLAKE.ACCOUNT_USAGE.ACCESS_HISTORY, que tiene latencia de hasta tres horas. En una sesion de 30 minutos no alcanza a poblarse, por eso el paso usa INFORMATION_SCHEMA.QUERY_HISTORY, que es inmediato. Vale decirlo en vez de mostrar una tabla vacia.
-- retencion de auditoria: el pliego pide 3 meses en linea y 9 fuera
SHOW PARAMETERS LIKE 'DATA_RETENTION_TIME_IN_DAYS' IN DATABASE CB_SILVER;
CALL CB_PLATAFORMA.EVIDENCIA.LOG_EVIDENCIA('T1',
    'Trazabilidad de acceso al dato de tarjeta por usuario y rol',
    'INFORMATION_SCHEMA.QUERY_HISTORY sobre TARJETAHABIENTES',
    'Rastro inmediato de quien consulto la tabla con PAN y con que rol, sin instrumentar la aplicacion',
    'Anexo 10 - 4.5 trazabilidad y auditoria de accesos');

Que preguntar al otro proveedor

Cuanta latencia tiene la auditoria y quien la instrumenta. Pregunten cuanto tarda en aparecer un acceso en el log, si el rastro se genera solo o depende de que la aplicacion lo reporte, y si un usuario con privilegios puede borrar su propio rastro.
6

Borrado seguro verificable

Demostrar que un dato borrado no se puede recuperar. Es requisito eliminatorio.
4 min

El requisito eliminatorio 4 pide borrado seguro verificable. Verificable significa que se pueda intentar recuperar el dato y fallar, delante de todos.

USE ROLE ACCOUNTADMIN;
USE WAREHOUSE WH_GOBIERNO;

-- extraccion temporal de datos de tarjeta, del tipo que se crea para un
-- analisis puntual y despues hay que eliminar sin rastro
CREATE OR REPLACE TABLE CB_SILVER.ADQUIRENCIA.PAN_TEMPORAL
    DATA_RETENTION_TIME_IN_DAYS = 0
AS SELECT TARJETAHABIENTE_ID, PAN
   FROM CB_SILVER.ADQUIRENCIA.TARJETAHABIENTES
   LIMIT 1000;

SELECT COUNT(*) AS FILAS_ANTES FROM CB_SILVER.ADQUIRENCIA.PAN_TEMPORAL;

-- la ventana de recuperacion es cero por construccion, no por procedimiento
SHOW TABLES LIKE 'PAN_TEMPORAL' IN SCHEMA CB_SILVER.ADQUIRENCIA;
SELECT "name", "retention_time" FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()));
Resultado esperado. retention_time = 0.
DROP TABLE CB_SILVER.ADQUIRENCIA.PAN_TEMPORAL;

-- intentar recuperarla: debe fallar
UNDROP TABLE CB_SILVER.ADQUIRENCIA.PAN_TEMPORAL;
Resultado esperado. 090025: Table PAN_TEMPORAL did not exist or was purged. El error es el resultado buscado. No hay Time Travel, no hay Fail-safe, no hay recuperacion por soporte.
Atencion. Este mismo control es el que sostiene el derecho al olvido: la ventana de recuperacion se declara en el objeto y la plataforma la respeta, sin depender de que alguien ejecute un procedimiento de purga.
CALL CB_PLATAFORMA.EVIDENCIA.LOG_EVIDENCIA('T1',
    'Borrado seguro verificable de una extraccion con dato de tarjeta',
    'CB_SILVER.ADQUIRENCIA.PAN_TEMPORAL con DATA_RETENTION_TIME_IN_DAYS = 0',
    'UNDROP fallo con did not exist or was purged. Sin Time Travel ni Fail-safe: la ventana de recuperacion es cero por construccion',
    'Anexo 10 - 3.6 borrado seguro y derecho al olvido (eliminatorio)');

Que preguntar al otro proveedor

Que el borrado se pueda comprobar intentando recuperar el dato. Muchas plataformas responden con la politica de retencion del almacenamiento subyacente, que no es lo mismo. Pidan crear una tabla, borrarla e intentar recuperarla en la sesion. Si la respuesta es que hay que abrir un caso con soporte para purgar, eso no es borrado verificable.
