El incidente de las 3:00 AM

Una cuenta de servicio empezó a exfiltrar datos de madrugada. En una hora vas a detectarlo, contenerlo y prevenir que vuelva a pasar — usando Snowflake y dejando que Coco escriba el SQL contigo.

⏱ 60 minutos 🔐 Seguridad 🏛 Gobierno 🛠 Desarrollo ☁️ Datos en S3 (~50M filas)
Arma hol_incidente_3am.sql con todos los bloques del lab, en orden.

De qué se trata

Este es un HOL integrado: un solo hilo narrativo que atraviesa tres perfiles técnicos. Cada acto resuelve una parte del incidente y termina con un artefacto concreto. Los datos son sintéticos, viven en un bucket de S3 y los cargas a Snowflake vía stage.

  • 00–06Setup. Creas el entorno y cargas ~50M filas desde S3.
  • 06–24SeguridadActo 1 · Detectar. Coco escribe las queries de caza: fuerza bruta, viaje imposible y el pico de exfiltración.
  • 24–42GobiernoActo 2 · Contener. Clasificas PII, aplicas enmascaramiento y política de fila, y mides el impacto.
  • 42–56DesarrolloActo 3 · Prevenir. Monitoreo continuo — app en contenedor (Amb 1) o agente conversacional (Amb 2).
  • 56–60Cierre. Qué construiste y hacia dónde escalarlo.
Dos ambientes, una misma historia. Los Actos 1 y 2 son idénticos para todos (SQL puro + Coco). El Acto 3 se bifurca: si tienes terminal y Podman sigues la ruta full-stack; si solo tienes la UI de Snowflake, construyes un agente. Verás pestañas Ambiente 1 / Ambiente 2 donde el camino cambia.

00. Setup — entorno y carga desde S3

Abre una worksheet en Snowsight (o Coco Desktop) y ejecuta el bloque. Crea el entorno, un stage sobre el bucket S3 del lab, y carga las tres tablas (~50M filas).

Credenciales: reemplaza <AWS_KEY_ID> y <AWS_SECRET_KEY> por la llave IAM read-only que te entrega el instructor. No se publican en esta página.
CREATE DATABASE IF NOT EXISTS HOL_SEC;
CREATE SCHEMA IF NOT EXISTS HOL_SEC.INCIDENTE;
CREATE WAREHOUSE IF NOT EXISTS HOL_WH
  WAREHOUSE_SIZE = XSMALL AUTO_SUSPEND = 60 AUTO_RESUME = TRUE;

USE SCHEMA HOL_SEC.INCIDENTE;
USE WAREHOUSE HOL_WH;

-- Formato y stage sobre el bucket S3 del lab
CREATE OR REPLACE FILE FORMAT ff_csv_gz
  TYPE = CSV FIELD_DELIMITER = ';' SKIP_HEADER = 1
  FIELD_OPTIONALLY_ENCLOSED_BY = '"' COMPRESSION = GZIP;

CREATE OR REPLACE STAGE stg_hol
  URL = 's3://demosjparrado/hol_ach_2/'
  CREDENTIALS = (AWS_KEY_ID = '<AWS_KEY_ID>' AWS_SECRET_KEY = '<AWS_SECRET_KEY>')
  FILE_FORMAT = ff_csv_gz;

-- Tablas destino
CREATE OR REPLACE TABLE AUTH_LOGINS (
  event_id  NUMBER, event_ts TIMESTAMP_NTZ, user_name STRING,
  city STRING, country STRING, client_ip STRING, status STRING);

CREATE OR REPLACE TABLE EXPORT_EVENTS (
  export_id NUMBER, export_ts TIMESTAMP_NTZ, user_name STRING, bytes_out NUMBER);

CREATE OR REPLACE TABLE CUSTOMERS (
  customer_id NUMBER, full_name STRING, email STRING,
  national_id STRING, card_last4 STRING, branch_city STRING);

-- Carga desde S3
COPY INTO AUTH_LOGINS   FROM @stg_hol/auth_logins/;
COPY INTO EXPORT_EVENTS FROM @stg_hol/export_events/;
COPY INTO CUSTOMERS     FROM @stg_hol/customers/;

-- Verificación de conteos
SELECT 'AUTH_LOGINS' AS tabla, COUNT(*) AS filas FROM AUTH_LOGINS
UNION ALL SELECT 'EXPORT_EVENTS', COUNT(*) FROM EXPORT_EVENTS
UNION ALL SELECT 'CUSTOMERS', COUNT(*) FROM CUSTOMERS;
Por qué desde S3: es el patrón real de ingesta — datos en el data lake, Snowflake los carga a escala. Conteos esperados: 20.000.242 · 25.001.030 · 5.000.000.

Seguridad01. Detectar — caza de amenazas con Coco

No escribas el SQL a mano: descríbele a Coco qué buscas. Debajo de cada prompt dejamos el SQL de referencia (que también entra al script descargable).

1.1 · Fuerza bruta

Pídele a Coco

"Sobre AUTH_LOGINS, encuentra usuarios con 10 o más logins fallidos en ventanas de 10 minutos. Muéstrame usuario, ventana y número de fallos."

-- Deteccion: fuerza bruta
SELECT user_name,
       TIME_SLICE(event_ts, 10, 'MINUTE') AS ventana,
       COUNT(*) AS fallos
FROM AUTH_LOGINS
WHERE status = 'FAIL'
GROUP BY 1, 2
HAVING COUNT(*) >= 10
ORDER BY fallos DESC;

Resultado esperado: svc_etl con 40 fallos en la ventana de las 02:00.

1.2 · Viaje imposible

Pídele a Coco

"Para cada usuario, detecta dos logins exitosos consecutivos desde países distintos con menos de 3 horas de diferencia. Usa LAG particionando por usuario."

-- Deteccion: viaje imposible
WITH s AS (
  SELECT user_name, event_ts, country,
         LAG(country)  OVER (PARTITION BY user_name ORDER BY event_ts) AS prev_country,
         LAG(event_ts) OVER (PARTITION BY user_name ORDER BY event_ts) AS prev_ts
  FROM AUTH_LOGINS
  WHERE status = 'SUCCESS'
)
SELECT user_name, prev_country, country, prev_ts, event_ts
FROM s
WHERE prev_country IS NOT NULL
  AND country <> prev_country
  AND TIMESTAMPDIFF('hour', prev_ts, event_ts) < 3;

Resultado esperado: solo svc_etl, con un salto CO → DE (00:30 → 02:30).

1.3 · Pico de exfiltración

Pídele a Coco

"Agrega EXPORT_EVENTS por hora y usuario. Marca como anómalas las horas cuyo total de bytes_out supere 3 desviaciones estándar sobre la media del usuario."

-- Deteccion: exfiltracion anomala (>3 sigma)
WITH h AS (
  SELECT user_name, DATE_TRUNC('hour', export_ts) AS hora, SUM(bytes_out) AS bytes_hora
  FROM EXPORT_EVENTS GROUP BY 1, 2
), stats AS (
  SELECT user_name, AVG(bytes_hora) AS media, STDDEV(bytes_hora) AS ds
  FROM h GROUP BY 1
)
SELECT h.user_name, h.hora, ROUND(h.bytes_hora/1e6, 1) AS mb_hora
FROM h JOIN stats s ON h.user_name = s.user_name
WHERE h.bytes_hora > s.media + 3 * COALESCE(s.ds, 0)
ORDER BY h.bytes_hora DESC;

Resultado esperado: svc_etl encabeza con ~8.635 MB a las 03:00 — muy por encima de cualquier usuario normal.

Skill opcional: invoca el skill security-investigation para que Coco arme la investigación completa (anomalías de login → exfiltración → cuentas afectadas) como un flujo guiado.
Conclusión del acto: los tres hilos convergen en svc_etl. Tienes al culpable y la ventana temporal. Ahora hay que contener el daño sobre los datos que tocó.

Gobierno02. Contener — clasificar y blindar la PII

La cuenta comprometida leyó CUSTOMERS. Antes de que vuelva a pasar, gobierna esa tabla.

2.1 · Clasificación automática de PII

-- Clasificacion automatica (auto-tag de categorias semanticas)
SELECT SYSTEM$CLASSIFY('HOL_SEC.INCIDENTE.CUSTOMERS', {'auto_tag': true});
Pídele a Coco

"Interpreta el resultado de la clasificación de CUSTOMERS y dime qué columnas son identificadores directos y cuáles cuasi-identificadores."

2.2 · Enmascaramiento dinámico

Pídele a Coco

"Crea una masking policy que muestre el valor completo solo a ACCOUNTADMIN/SECURITYADMIN y enmascare al resto. Aplícala a email y national_id."

-- Enmascaramiento dinamico de PII
CREATE OR REPLACE MASKING POLICY mask_pii AS (val STRING) RETURNS STRING ->
  CASE
    WHEN CURRENT_ROLE() IN ('ACCOUNTADMIN','SECURITYADMIN') THEN val
    ELSE '*** REDACTED ***'
  END;

ALTER TABLE CUSTOMERS MODIFY COLUMN email       SET MASKING POLICY mask_pii;
ALTER TABLE CUSTOMERS MODIFY COLUMN national_id SET MASKING POLICY mask_pii;

2.3 · Política de acceso por fila (least privilege)

Pídele a Coco

"Crea una row access policy sobre CUSTOMERS: ACCOUNTADMIN ve todo; un rol regional solo ve filas de su ciudad."

-- Acceso por fila segun rol/sucursal
CREATE OR REPLACE ROW ACCESS POLICY rap_branch AS (branch STRING) RETURNS BOOLEAN ->
  CASE
    WHEN CURRENT_ROLE() IN ('ACCOUNTADMIN','SECURITYADMIN') THEN TRUE
    WHEN CURRENT_ROLE() = 'ANALISTA_BOGOTA' THEN branch = 'Bogota'
    ELSE FALSE
  END;

ALTER TABLE CUSTOMERS ADD ROW ACCESS POLICY rap_branch ON (branch_city);

2.4 · Triage de alertas con IA

-- Triage automatico de severidad con Cortex AI
SELECT user_name,
       AI_CLASSIFY('Actividad sospechosa de ' || user_name ||
                   ': exportacion anomala y viaje imposible',
                   ['critico','alto','medio','bajo']):labels[0]::STRING AS severidad
FROM (
  SELECT DISTINCT user_name FROM EXPORT_EVENTS WHERE bytes_out > 150000000
);

2.5 · Impacto antes de actuar

Pídele a Coco

"¿Qué vistas, tablas dinámicas o dashboards dependen de CUSTOMERS? Antes de revocar accesos, dime qué se rompería."

Cuidado: revocar en caliente puede tumbar pipelines legítimos. El skill lineage le permite a Coco calcular el "blast radius" antes de que toques un grant.
Conclusión del acto: la PII quedó clasificada, enmascarada y restringida por fila, con el impacto medido. El daño está contenido.

Desarrollo03. Prevenir — monitoreo continuo

Contener no basta: necesitas algo que vigile solo. Aquí el camino se bifurca según tu ambiente.

Coco Desktop · Node.js · Snowflake CLI · Podman

3.1 · Pipeline incremental de detección

Pídele a Coco

"Crea una dynamic table incremental que mantenga, por usuario y hora, el total de bytes_out, con target lag de 1 minuto."

-- Pipeline incremental de exfiltracion por hora
CREATE OR REPLACE DYNAMIC TABLE DT_EXFIL_HORA
  TARGET_LAG = '1 minute' WAREHOUSE = HOL_WH AS
SELECT user_name,
       DATE_TRUNC('hour', export_ts) AS hora,
       SUM(bytes_out) AS bytes_hora
FROM EXPORT_EVENTS
GROUP BY 1, 2;

3.2 · Escalado elástico

Cambiar el tamaño del warehouse es instantáneo y se factura por segundo. Recarga EXPORT_EVENTS con distintos tamaños y compáralo en tu cuenta.

-- Escalado elastico: recargar EXPORT_EVENTS con distintos tamanos
ALTER WAREHOUSE HOL_WH SET WAREHOUSE_SIZE = SMALL;
TRUNCATE TABLE EXPORT_EVENTS;
COPY INTO EXPORT_EVENTS FROM @stg_hol/export_events/ FORCE = TRUE;

ALTER WAREHOUSE HOL_WH SET WAREHOUSE_SIZE = XLARGE;
TRUNCATE TABLE EXPORT_EVENTS;
COPY INTO EXPORT_EVENTS FROM @stg_hol/export_events/ FORCE = TRUE;

ALTER WAREHOUSE HOL_WH SET WAREHOUSE_SIZE = XSMALL;
Gotcha: TRUNCATE no borra el historial de carga de COPY, así que el segundo COPY omitiría los archivos. Por eso va FORCE = TRUE.
Qué esperar a esta escala: recargar 25M filas (28 archivos) toma pocos segundos tanto en SMALL como en XLARGE — a este volumen la carga ya es paralela y rápida. El diferencial de tamaño se nota en cargas mucho mayores o en consultas analíticas pesadas. El mensaje clave: elasticidad instantánea y facturación por segundo, sin reprovisionar infraestructura.
