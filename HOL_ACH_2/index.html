El incidente de las 3:00 AM

De madrugada, un comercio empieza a recibir una avalancha de pagos PSE y un banco dispara sus rechazos. En una hora vas a detectar el fraude, contener el riesgo y prevenir que se repita — sobre datos PSE reales en escala y un flujo en tiempo real, con Coco escribiendo el SQL contigo.

⏱ 60 minutos 💳 PSE 🔐 Seguridad 🏛 Gobierno 🛠 Desarrollo ☁️ ~30M txns en S3 + feed en vivo
Arma hol_ach_pse.sql con todos los bloques del lab, en orden.

De qué se trata

ACH procesa pagos 24/7. Este HOL usa ese mismo pulso: un histórico de ~30M transacciones PSE en S3 y un feed en tiempo real que sigue llegando durante la sesión. Un solo hilo narrativo atraviesa tres perfiles y cada acto entrega un artefacto concreto.

  • 00–06Setup. Entorno + carga del histórico PSE desde S3.
  • 06–24SeguridadActo 1 · Detectar. Coco escribe la caza de fraude: rechazos por banco, velocity por documento, monto atípico y comercio bajo ataque.
  • 24–42GobiernoActo 2 · Contener. Clasificas el documento, aplicas enmascaramiento y acceso por entidad, y triage con IA.
  • 42–56DesarrolloActo 3 · Prevenir. Ingesta en tiempo real (Snowpipe + Dynamic Tables) y un dashboard que se actualiza solo.
  • 56–60Cierre. Qué construiste y cómo escalarlo.
Dos ambientes, una misma historia. Los Actos 1 y 2 son idénticos (SQL puro + Coco). El Acto 3 se bifurca: con terminal y Podman despliegas un dashboard en SPCS/Streamlit; con solo la UI construyes un Cortex Agent para Snowflake CoWork. Verás pestañas donde el camino cambia.

Seguridad01. Detectar — caza de fraude PSE con Coco

No escribas el SQL a mano: descríbele a Coco qué buscas. Debajo dejamos el SQL de referencia (también entra al script descargable).

1.1 · Pico de rechazos por banco

Pídele a Coco

"Sobre PSE_TRANSACTIONS, dame por banco y por hora el número de rechazos y el % de rechazo. Ordena por rechazos."

-- Deteccion: rechazos anomalos por banco/hora
SELECT banco, DATE_TRUNC('hour', ts) AS hora,
       COUNT(*) AS total,
       SUM(IFF(estado='RECHAZADA',1,0)) AS rechazos,
       ROUND(100*SUM(IFF(estado='RECHAZADA',1,0))/COUNT(*),1) AS pct_rechazo
FROM PSE_TRANSACTIONS
GROUP BY 1,2
HAVING rechazos > 500
ORDER BY rechazos DESC;

Resultado esperado: Scotiabank Colpatria a las 03:00 con ~1.605 rechazos (57,3% vs ~9% normal) — posible caída o ataque contra ese banco.

1.2 · Velocity por documento (card testing)

Pídele a Coco

"Encuentra documentos con 15 o más transacciones en ventanas de 10 minutos. Muéstrame documento, ventana y número de transacciones."

-- Deteccion: velocity por documento
SELECT documento_hash,
       TIME_SLICE(ts, 10, 'MINUTE') AS ventana,
       COUNT(*) AS txns
FROM PSE_TRANSACTIONS
GROUP BY 1,2
HAVING COUNT(*) >= 15
ORDER BY txns DESC;

Resultado esperado: un grupo de documentos DOC900000xx con 20–25 txns en 10 minutos, todas hacia el mismo comercio — el anillo de fraude.

1.3 · Monto atípico por comercio

Pídele a Coco

"Marca las transacciones cuyo monto supere 3 desviaciones estándar sobre la media global y agrúpalas por comercio, ordenando por el monto máximo."

-- Deteccion: montos atipicos (>3 sigma)
WITH s AS (SELECT AVG(monto) AS mu, STDDEV(monto) AS sd FROM PSE_TRANSACTIONS)
SELECT comercio_id, COUNT(*) AS n, ROUND(MAX(monto)/1e6,1) AS max_mcop
FROM PSE_TRANSACTIONS, s
WHERE monto > s.mu + 3*s.sd
GROUP BY 1
ORDER BY max_mcop DESC;

Resultado esperado: el comercio 9001 encabeza con montos de hasta ~199 millones COP, muy por encima del máximo normal (~20 millones).

1.4 · Comercio bajo ataque

Pídele a Coco

"Por comercio y ventana de 10 minutos, cuenta transacciones y documentos distintos. Muéstrame los comercios con picos de volumen."

-- Deteccion: comercio bajo ataque (concentracion anomala)
SELECT comercio_id,
       TIME_SLICE(ts, 10, 'MINUTE') AS ventana,
       COUNT(*) AS txns,
       COUNT(DISTINCT documento_hash) AS documentos,
       ROUND(SUM(monto)/1e6,1) AS mcop
FROM PSE_TRANSACTIONS
GROUP BY 1,2
HAVING COUNT(*) > 300
ORDER BY txns DESC;

Resultado esperado: el comercio 9001 domina las ventanas de 03:00 a 03:20 con cientos de transacciones — el objetivo del anillo.

Skill opcional: invoca security-investigation para que Coco arme la investigación completa (rechazos → velocity → comercio objetivo) como un flujo guiado.
Conclusión: las cuatro señales convergen en el comercio 9001 y el anillo DOC900000xx, con un banco (Scotiabank) bajo estrés. Tienes el fraude y su ventana. Toca contener.

Gobierno02. Contener — gobernar el dato sensible

Las transacciones exponen el documento del pagador. Antes de compartir tableros o dar acceso a más analistas, gobierna la tabla.

2.1 · Clasificación automática

-- Clasificacion automatica de categorias semanticas / PII
SELECT SYSTEM$CLASSIFY('HOL_SEC.INCIDENTE.PSE_TRANSACTIONS', {'auto_tag': true});
Pídele a Coco

"Interpreta la clasificación de PSE_TRANSACTIONS y dime qué columnas son identificadores sensibles."

2.2 · Enmascaramiento del documento

Pídele a Coco

"Crea una masking policy que muestre el documento completo solo a ACCOUNTADMIN/SECURITYADMIN y lo enmascare al resto. Aplícala a documento_hash."

-- Enmascaramiento dinamico del documento
CREATE OR REPLACE MASKING POLICY mask_doc AS (val STRING) RETURNS STRING ->
  CASE WHEN CURRENT_ROLE() IN ('ACCOUNTADMIN','SECURITYADMIN') THEN val
       ELSE 'DOC-****' END;
ALTER TABLE PSE_TRANSACTIONS MODIFY COLUMN documento_hash SET MASKING POLICY mask_doc;

2.3 · Acceso por fila (por banco / entidad)

Pídele a Coco

"Crea una row access policy: ACCOUNTADMIN ve todo; un rol de un banco solo ve las transacciones originadas en ese banco."

-- Acceso por fila segun banco de la entidad
CREATE OR REPLACE ROW ACCESS POLICY rap_banco AS (banco STRING) RETURNS BOOLEAN ->
  CASE WHEN CURRENT_ROLE() IN ('ACCOUNTADMIN','SECURITYADMIN') THEN TRUE
       WHEN CURRENT_ROLE() = 'ENTIDAD_BANCOLOMBIA' THEN banco = 'Bancolombia'
       ELSE FALSE END;
ALTER TABLE PSE_TRANSACTIONS ADD ROW ACCESS POLICY rap_banco ON (banco);

2.4 · Triage de alertas con IA

-- Severidad automatica de la alerta con Cortex AI
SELECT comercio_id,
       AI_CLASSIFY('Comercio ' || comercio_id ||
         ' con pico de transacciones y montos atipicos de madrugada',
         ['critico','alto','medio','bajo']):labels[0]::STRING AS severidad
FROM (SELECT DISTINCT comercio_id FROM PSE_TRANSACTIONS WHERE monto > 80000000);

2.5 · Impacto antes de actuar

Pídele a Coco

"¿Qué vistas, tablas dinámicas o dashboards dependen de PSE_TRANSACTIONS? Antes de bloquear un comercio o revocar accesos, dime qué se rompería."

Cuidado: bloquear en caliente puede tumbar liquidación o reportes legítimos. El skill lineage le permite a Coco calcular el "blast radius" antes de tocar un grant.
Conclusión: el documento quedó enmascarado, el acceso restringido por entidad y la alerta priorizada, con el impacto medido.

Desarrollo03. Prevenir — monitoreo en tiempo real

Contener no basta: ACH opera 24/7, así que necesitas vigilancia continua. Vas a montar el pulso real de PSE.

Arquitectura del "tiempo real":
feeder deja archivos en S3 cada ~15 s → Snowpipe (auto-ingest) los carga solo → Dynamic Tables (lag 1 min) mantienen los agregados frescos → el dashboard los lee y se actualiza solo. El instructor arranca el feeder al iniciar la sesión.

3.1 · Ingesta continua con Snowpipe

-- PIPE con auto-ingest sobre el prefijo del feed
CREATE OR REPLACE PIPE pse_pipe
  AUTO_INGEST = TRUE
AS
COPY INTO PSE_TRANSACTIONS
FROM @stg_hol/pse_stream/
FILE_FORMAT = (FORMAT_NAME = ff_csv_gz);

-- Obtén el ARN de la cola de notificación (columna notification_channel)
SHOW PIPES LIKE 'pse_pipe';

Toma el notification_channel (un ARN de SQS) y configura la notificación de eventos del bucket para el prefijo del feed (una sola vez, del lado AWS):

# Configurar evento S3 -> SQS de Snowpipe (filtrado al prefijo del feed)
aws s3api put-bucket-notification-configuration --bucket demosjparrado \
  --notification-configuration '{"QueueConfigurations":[{
    "QueueArn":"<NOTIFICATION_CHANNEL_ARN>",
    "Events":["s3:ObjectCreated:*"],
    "Filter":{"Key":{"FilterRules":[{"Name":"prefix","Value":"hol_ach_2/pse_stream/"}]}}}]}'
Alternativa sin notificaciones: si no puedes configurar el evento del bucket, reemplaza el PIPE por una TASK serverless cada 1 min con COPY INTO PSE_TRANSACTIONS FROM @stg_hol/pse_stream/ — el historial de carga evita reprocesar archivos.

3.2 · Dynamic Tables (agregados frescos)

-- Volumen y monto por minuto / banco / estado
CREATE OR REPLACE DYNAMIC TABLE DT_PSE_POR_MINUTO
  TARGET_LAG = '1 minute' WAREHOUSE = HOL_WH AS
SELECT DATE_TRUNC('minute', ts) AS minuto, banco, estado,
       COUNT(*) AS txns, SUM(monto) AS monto_total
FROM PSE_TRANSACTIONS GROUP BY 1,2,3;

-- Tasa de rechazo por banco / hora
CREATE OR REPLACE DYNAMIC TABLE DT_PSE_RECHAZOS
  TARGET_LAG = '1 minute' WAREHOUSE = HOL_WH AS
SELECT DATE_TRUNC('hour', ts) AS hora, banco,
       COUNT(*) AS total,
       SUM(IFF(estado='RECHAZADA',1,0)) AS rechazos,
       ROUND(100*SUM(IFF(estado='RECHAZADA',1,0))/COUNT(*),1) AS pct_rechazo
FROM PSE_TRANSACTIONS GROUP BY 1,2;

-- Concentracion por comercio / ventana 10 min
CREATE OR REPLACE DYNAMIC TABLE DT_PSE_COMERCIO_ATAQUE
  TARGET_LAG = '1 minute' WAREHOUSE = HOL_WH AS
SELECT comercio_id, TIME_SLICE(ts, 10, 'MINUTE') AS ventana,
       COUNT(*) AS txns, SUM(monto) AS monto_total
FROM PSE_TRANSACTIONS GROUP BY 1,2;
Comprobación en vivo: consulta DT_PSE_POR_MINUTO ordenando por minuto descendente varias veces — con el feeder corriendo verás minutos nuevos apareciendo sin que ejecutes ninguna carga.
